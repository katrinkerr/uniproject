### Командна конвенція програмного коду
Ця конвенція визначає спільні правила написання, оформлення, документування та перевірки програмного коду Plot.

Мета — забезпечити читабельність коду, його підтримку, узгодженість між розробниками та ефективну командну роботу.

Конвенція поширюється на frontend- і backend-розробку. Для кожної технології використовуються відповідні стандарти.


### 1. Frontend — Angular / TypeScript

Основою є рекомендації Angular Style Guide та прийняті правила TypeScript.

***1.1. Найменування***

Змінні та функції: camelCase — userEmail, getUserData().

Класи та інтерфейси: PascalCase — AuthService, UserProfile.

Назви файлів: kebab-case — user-profile.

Файли компонентів і сервісів: дотримуємося вже прийнятого в проєкті формату, наприклад login.component.ts, auth.service.ts.

Константи: використовуємо зрозумілі імена з урахуванням стилю TypeScript та наявного коду.

***1.2. Форматування***

Використовуємо пробіли замість табуляцій.

Відступи — 2 пробіли, якщо це відповідає налаштуванням проєкту.

Дотримуємося однакового стилю лапок, крапок із комою та перенесення рядків.

Для автоматичного форматування використовуємо Prettier після його налаштування в проєкті

***1.3. Структура коду***

Компоненти відповідають переважно за відображення інтерфейсу та взаємодію з користувачем.

Роботу з HTTP-запитами виносимо в сервіси.

Для захисту маршрутів використовуємо Angular Guards.

Для опису даних використовуємо TypeScript-типи та інтерфейси.

Уникаємо дублювання логіки в різних компонентах.

Дотримуємося наявної структури Angular-проєкту.

 ### 2. Backend — Python / FastAPI

Основою є стандарт оформлення Python-коду **PEP 8** та рекомендації щодо написання читабельного й зрозумілого коду.

***2.1. Найменування***

Змінні та функції: **snake_case** — `user_email`, `password_hash`, `get_user_data()`.

Класи: **PascalCase** — `User`, `RegisterRequest`, `LoginResponse`.

Константи: **UPPER_SNAKE_CASE** — `MAX_PASSWORD_LENGTH`, `SESSION_LIFETIME`.

Назви файлів і модулів: **snake_case** — `auth.py`, `models.py`, `test_auth.py`.

Назви таблиць і полів бази даних: **snake_case** — `users`, `password_hash`, `created_at`.

API endpoints: використовуємо малі літери та зрозумілі назви — `/auth/register`, `/auth/login`, `/missions/random`.

Усі назви змінних, функцій, класів і файлів пишемо англійською мовою. Уникаємо незрозумілих скорочень.

***2.2. Форматування***

Використовуємо 4 пробіли для відступів замість табуляцій.

Дотримуємося рекомендацій **PEP 8**.

Рекомендована максимальна довжина рядка — 88 символів.

Для рядків переважно використовуємо подвійні лапки `" "`.

Використовуємо зрозумілі назви змінних і функцій.

За можливості застосовуємо анотації типів (*type hints*) для параметрів функцій та значень, які вони повертають.

Імпорти групуємо в такому порядку: стандартна бібліотека Python, сторонні бібліотеки, власні модулі проєкту.

Для автоматичної перевірки стилю та форматування коду рекомендується **Ruff** (`ruff check`, `ruff format`).

***2.3. Організація коду***

Дотримуємося наявної структури FastAPI-проєкту, не створюючи зайвих модулів і папок без необхідності.

Головний файл `main.py` використовується для ініціалізації застосунку та підключення API-маршрутів.

Логіку окремих функціональних частин розміщуємо у відповідних модулях, наприклад `auth.py` для реєстрації та авторизації.

Для опису структури запитів і відповідей API використовуємо моделі **Pydantic**.

Для роботи з базою даних використовуємо **SQLAlchemy**. Моделі таблиць описуємо в `models.py`, а зміни структури БД оформлюємо окремими міграціями.

Обробляємо помилки та використовуємо відповідні HTTP-статуси (`200`, `201`, `401`, `409`, `422` тощо).

Не зберігаємо паролі у відкритому вигляді. Конфіденційні дані та локальні файли конфігурації не додаємо до Git.

Автоматичні тести пишемо за допомогою **Pytest** і розміщуємо в папці `tests/`. Назви тестових файлів починаються з `test_`, наприклад `test_auth.py`.

Для тестування бази даних використовуємо окреме тестове середовище, щоб не змінювати робочі дані.

Документацію API зберігаємо в `docs/api/` та оновлюємо відповідно до реалізованих функцій.

Уникаємо дублювання коду. Функції повинні мати зрозуміле призначення, а складну логіку за необхідності розділяємо на менші функції.

Коментарі та документацію пишемо англійською мовою, пояснюючи насамперед неочевидні рішення, а не кожну окрему інструкцію.
